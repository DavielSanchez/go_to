# Release v0.3.2 — Finalización funcional por roles

Fecha: 5 de julio de 2026  
Estado: lista para piloto  
Tipo: funcionalidad, experiencia de usuario y estabilización

## Objetivo

Cerrar las observaciones del piloto por rol, eliminar interacciones simuladas y dejar los flujos conectados a la API y MongoDB con datos persistentes, permisos y casos de prueba reproducibles.

## Cambios por rol

### Empleado

- El QR creció a 144 px y puede abrirse en un visor de 300 px al pulsarlo.
- Después de confirmar se presenta un estado explícito de confirmación, no el formulario inicial.
- La acción secundaria **Eliminar confirmación** permite revertir la decisión dentro de la ventana permitida.
- Confirmar, rechazar o cancelar se valida también en el servidor. El límite predeterminado es 21:00; la API devuelve `deadline`, `cutoff` y `canModify`.
- Una operación fuera de tiempo responde HTTP 409 con código `CONFIRMATION_CLOSED`; la interfaz bloquea las acciones y explica el motivo.
- Las excepciones se registran mediante diálogo propio de Vía.

### Conductor

- Se sustituyó el tablero anterior por un flujo de abordaje persistente y compatible con React Strict Mode.
- El inicio y liberación de cámara ahora tolera montajes dobles, permisos rechazados y dispositivos sin cámara.
- Se mantiene entrada manual de BMS cuando no existe cámara disponible.
- Los abordajes normales, duplicados y ad hoc se validan en API y se almacenan en MongoDB.
- El inicio de viaje con pasajeros pendientes utiliza un diálogo propio y requiere confirmación explícita.

### Supervisor

- La bandeja de excepciones presenta carga, datos reales y un estado vacío ilustrado cuando no existen pendientes.
- Aprobar o rechazar usa un diálogo propio, registra decisión, comentario, auditoría y notificación.

### Workforce

- El dashboard general fue sustituido por uno especializado con métricas de cobertura, empleados programados, turnos e incidencias.
- Se añadió descarga de plantilla Excel junto a **Importar**.
- La plantilla contiene `bms`, fecha, horas, días laborables, horas extra y motivo.
- Sin empleado seleccionado se muestra un estado vacío explícito e ilustrado.
- La edición de horario usa un diálogo propio y guarda mediante API.

### Recursos Humanos

- Se añadió dashboard especializado con métricas de plantilla activa, departamentos, empleados elegibles e incidencias.
- **Nuevo empleado**, **Importar** y **Descargar plantilla** están agrupados en la misma barra.
- Cada fila de persona es editable; RR. HH. puede actualizar identidad, contacto, organización, ubicación, elegibilidad y estado activo.
- La plantilla Excel de empleados está disponible mediante endpoint autenticado.

## Cambios generales

- Sidebar móvil y panel de notificaciones se cierran al pulsar fuera.
- Se implementó un sistema global de diálogos con la UI de Vía; se retiraron `prompt()` y `confirm()` del código cliente.
- Se añadieron estados vacíos ilustrados en excepciones, horarios, personas e historial.
- Se habilitó un reporte operativo Excel real con hojas de solicitudes, rutas y abordajes.
- Se incorporaron usuarios de casos límite para probar rechazo y confirmación/asignación.
- Los archivos XLSX se generan como OpenXML en el servidor, sin ExcelJS; auditoría npm: 0 vulnerabilidades.

## API añadida o modificada

- `GET /api/templates/employees.xlsx` — plantilla de personas; roles `admin`, `hr`.
- `GET /api/templates/schedules.xlsx` — plantilla de horarios; roles `admin`, `workforce`.
- `GET /api/reports/summary.xlsx` — reporte operativo; roles `admin`, `operations`, `hr`, `supervisor`.
- `GET /api/requests` — incluye ventana de modificación.
- `POST /api/requests/confirm` — impide cambios después del límite.
- `POST /api/requests/cancel` — cancela antes del límite y persiste auditoría.

## Operación y despliegue

1. Configurar `.env` y un `JWT_SECRET` no compartido.
2. Iniciar MongoDB.
3. Ejecutar `npm install`.
4. En un ambiente de demostración limpio, ejecutar `npm run seed`. Este comando reinicia los datos; no debe utilizarse sobre producción con información real.
5. Ejecutar `npm run build` y `npm start`, o `npm run dev:all` para desarrollo.
6. Vite selecciona automáticamente su puerto disponible; la API permanece en el puerto configurado, 4000 por defecto.

## Validación de aceptación

- Seed completo con usuarios base y casos límite.
- Suite API: autenticación y RBAC, abordaje, duplicados, excepciones, inicio de viaje, aislamiento de tenant, límite de confirmación, plantillas y reporte.
- Build Vite de producción.
- Búsqueda estática sin usos de diálogos nativos en `src` o `server`.
- Auditoría de dependencias sin vulnerabilidades conocidas.

## Consideraciones para piloto

- Cámara y notificaciones del navegador requieren permisos del dispositivo y, fuera de localhost, HTTPS.
- Antes de producción deben reemplazarse las credenciales demo, restringirse CORS y programarse respaldos de MongoDB.
- La hora límite predeterminada es 21:00 y debe alinearse con la zona horaria operativa del servidor.
