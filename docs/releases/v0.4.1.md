# Release v0.4.1 — Gobierno y automatización de GitHub

Fecha: 5 de julio de 2026  
Estado: preparada para publicación  
Tipo: repositorio, integración continua y seguridad operativa

## Objetivo

Publicar el MVP con un flujo de colaboración reproducible, controles automatizados y separación explícita entre integración, aceptación y producción.

## Incorporado

- Ramas permanentes `main` y `develop` con convención para `feature/*`, `fix/*` y `hotfix/*`.
- CI para pushes y pull requests: instalación limpia, MongoDB 8, seed, 13 pruebas API, build Vite y artefacto del frontend.
- Workflow manual de promoción con entornos `development`, `staging` y `production`.
- Workflow de releases para tags SemVer `v*.*.*`, con notas automáticas y build comprimido.
- Dependabot semanal para npm y mensual para GitHub Actions, dirigido a `develop`.
- CODEOWNERS asignado a `@DavielSanchez`.
- Plantilla de pull request y formularios para errores y mejoras.
- Guía de contribución, política de seguridad y documento de gobierno del repositorio.
- Permisos mínimos explícitos y cancelación de ejecuciones CI obsoletas.

## Estrategia de integración

Los cambios ordinarios parten de `develop` y regresan mediante pull request. Una versión aceptada se integra de `develop` a `main`. Los hotfix parten de `main` y deben propagarse nuevamente a `develop`.

## Entornos

| Entorno | Uso | Control esperado |
|---|---|---|
| development | Integración y validación interna | Automatizable |
| staging | Prueba de aceptación del piloto | Aprobación del equipo |
| production | Datos y operación reales | Aprobación manual, secretos aislados y rama/tag restringido |

El workflow de promoción contiene el límite seguro donde se conectará el proveedor de hosting cuando sea elegido. No simula un despliegue que aún no existe.

## Configuración remota recomendada

Activar rulesets en GitHub para exigir el estado CI `validate`, pull requests, conversaciones resueltas, una aprobación en `main`, prohibición de force push y eliminación. En `production`, exigir aprobación del propietario y limitar despliegues a `main` o tags de versión.

## Validación

- El código funcional permanece idéntico a v0.4.0.
- Los scripts raíz siguen siendo la interfaz operativa.
- El CI replica el seed, pruebas y build ejecutados localmente.
- Ningún secreto ni archivo `.env` se versiona.
